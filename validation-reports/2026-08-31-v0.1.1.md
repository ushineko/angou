# Validation report — angou v0.1.1

**Date**: 2026-08-31
**Commit**: the release commit bumping `VERSION` and `README.md` to 0.1.1
**Spec**: [001 — container format, key model, store layout, and bootstrap](../specs/001-angou-format-keying-and-store.md)
**Scope**: first-run and cross-machine behaviour. No format, key model, or store layout
changes; a 0.1.0 store is read and written by this version unchanged.

---

## Summary

Every defect fixed here was found by using the tool rather than by testing it, and none
of them was a case of the program computing the wrong answer. They were cases where the
path a person takes through it did not exist, or led somewhere the documentation said it
would not. That is worth recording as a pattern: a suite of 75 end-to-end tests, written
against the design, did not catch a single one of them, because each test drove a path
the author already knew about.

## Phase 3 — Tests

| Gate | Result |
|---|---|
| `make test` (unit, `-race`) | pass — 7 packages |
| `make e2e` | pass — 75 tests |
| `make e2e-keyring` | **not run**, see below |
| `make e2e-container` | not implemented |
| `make shellcheck` | pass, including `install.sh` and `uninstall.sh` |

New coverage in this release:

- Decrypting on a machine other than the one that encrypted, in both directions, with
  the second machine given its own home directory, its own store path, no local key and
  no keyring. This is the store's primary purpose and previously had no test at all.
- A different passphrase failing to open a synced store.
- `init` with and without a keyring, and `--no-bootstrap`.
- Absolute, relative, and traversal-carrying paths given to `enc`.
- Every duration form `--ttl` accepts and several it must refuse.

**`make e2e-keyring` was not run in this cycle.** Opening a wallet raises a desktop
dialog that a non-interactive run cannot answer, and attempting it hung. The no-keyring
branch is covered by the automated suite; the keyring branch is covered by the gated
suite when a person runs it.

**The keyring path was instead verified by hand, on real hardware, and the full
cross-machine flow with it.** A store was created and set up on a KDE machine, a file
encrypted into it, and the store carried to a bare CachyOS machine on different
hardware, where `bootstrap.sh` installed a verified binary and the file was read back.
That is the design's central claim and it is the first time it has been executed outside
a temporary directory.

## Phase 4 — Code quality

`make lint` reports 0 issues at the pinned `golangci-lint v2.12.2`.

The keyring-setup half of `bootstrap` was extracted so `init` could use it rather than
being duplicated. The e2e suite no longer hardcodes the version string: twelve places
named `0.1.0-dev` and would have broken on this bump and every future one, and now ask
the binary what version it is.

## Phase 5 — Security review

**Dependency scan.** `govulncheck`: no vulnerabilities. No dependency changes since
0.1.0.

**Secrets.** No key material, passphrase, or store content is committed.

**Changes with a security dimension, and the reasoning applied to each:**

- `install.sh --publish-to` creates a release-signing key. It is opt-in rather than
  automatic, and the installer states where the key is and that it should be moved
  offline. Publishing automatically would have created, silently, exactly the
  configuration R5.4.1 exists to prevent: a signing key beside the store it signs for,
  where one compromise becomes code execution on every other machine that bootstraps.
  The key is reused rather than rotated across runs, because binaries installed
  elsewhere pin its fingerprint.
- `init` writing a local key by default widens what a compromise of that machine yields,
  from "the store, if they also have the passphrase" to "the store". This is the model
  R2.2 already describes for a bootstrapped machine and is what every machine reaches
  after `bootstrap` regardless; `init` now reaches it at a moment the user is present
  rather than at an arbitrary later one. `--no-bootstrap` declines it.
- Two hangs were introduced and removed during this work, both from probing the keyring
  by opening it. Opening a wallet can raise a dialog and wait for a person. A
  non-blocking check that the service is running is now used wherever the question is
  "is there a keyring" rather than "give me the keyring". A command that hangs while
  offering advice is worse than one that offers none.
- The plaintext digest was removed from verbose output in 0.1.0 and remains absent; the
  test asserting it covers the new `--verbose` call sites too.
- `localWallet` is now called under a five-second deadline. A kwalletd that holds the
  bus name without answering — wedged, or mid-crash — previously hung every angou
  command for the D-Bus default timeout. It was found on a real machine in that state,
  and "the keyring is broken" now degrades to the no-keyring path with an accurate
  reason rather than to a hang. `open` remains unbounded, because it can legitimately
  wait for a person to answer a dialog.

**Non-guarantees.** Unchanged from 0.1.0 and still asserted by tests: the agent excludes
other users and is not a boundary against processes running as the same user; the
installer's self-check is detection after execution; buffer zeroing is best-effort.

## Phase 5.5 — Release safety

**Rollback**: `git revert` the release commit, or reinstall 0.1.0. No format, store
layout, or key model change, so a store written by either version is readable by both.

**Migration**: none. A 0.1.0 store needs nothing done to it. A machine set up under
0.1.0 keeps working; the change to `init` affects only stores created after upgrading.

**Additive**: `--no-bootstrap`, `--publish-to`, and the extra `--ttl` forms are all new
surface. The one behaviour change is that `init` now sets up its machine, which is
declined with `--no-bootstrap`.

- The macOS Keychain backend is deferred; R2.5 covers the interim.
- The desktop navigator is not started.
