## Validation Report: v0.6.1 — Windows rename retry

**Date**: 2026-10-08
**Commit**: c87abd9 (chore: release 0.6.1), code from d19538b
**Status**: PASSED

Bootstrapping a Windows machine from the real Dropbox store with 0.6.0 failed
in the self-test: the index commit's rename was refused with "Access is
denied" while Dropbox held the old index. The self-test also left its probe
blob in the store. This release fixes both (spec 004 R1.4–R1.5).

### Phase 3: Tests

| Gate | Windows 11 26200, Go 1.27.0 (d19538b) | njv-cachyos, Go 1.27.1 (c87abd9) |
|------|---------------------------------------|----------------------------------|
| `make lint` | 0 issues | 0 issues |
| `make test` | all packages ok | all packages ok |
| `make e2e` (`-race`) | 141 pass, 5 skip, 0 fail | 145 pass, 1 skip, 0 fail |

Skips are the same as 0.6.0: agent tests on Windows, the Windows-only
refusal test on Linux. c87abd9 changes only `VERSION` and `README.md`.

New unit tests (Windows, `internal/fsx`):
- `TestRenameWaitsOutABriefHold`: holds the target open without
  `FILE_SHARE_DELETE`, asserts a plain `os.Rename` fails, releases after
  200 ms, and asserts `fsx.Rename` succeeds with the new content.
- `TestRenameGivesUpOnAHoldThatOutlastsTheTimeout`: returns
  `ERROR_ACCESS_DENIED` once the timeout passes.
- `TestRenameDoesNotRetryOtherErrors`: a missing source fails at once.

Diagnosis, before the fix: a probe in a throwaway Dropbox folder saw a rename
over a just-written file fail 7 times over 359 ms, then succeed; a rename over
a settled cloud placeholder succeeded first try. The hold is transient, so a
bounded retry is the fix rather than a different commit strategy.

- Status: ✓ PASSED
