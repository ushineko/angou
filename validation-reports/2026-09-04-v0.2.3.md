# Validation report — angou v0.2.3

**Date**: 2026-09-04
**Spec**: [001](../specs/001-angou.md) R5.4.1 (release-signing fingerprint)
**Scope**: `install.sh` only. No Go code changed; no container format, key model, or
store layout change.

---

## Summary

The release-signing fingerprint has to be compiled into a binary, and a binary without
one refuses to install anything from a store rather than trusting any signature it can
verify. That default is right for a machine with no key. It was also being applied to the
machine that *has* the key, because the fingerprint was read only under `--publish-to`:
an ordinary install on the signing machine produced a binary that could never install
from its own store, with the key sitting beside it the whole time. The fingerprint is now
read whenever the key file exists.

The second omission is narrower and had the same effect: `RELEASE_KEY` was passed to
`build-static` but not to `build-gui`, so even a publishing run installed a GUI that
refused every binary in the store while the CLI next to it accepted them.

Both were found by hitting the first one: after publishing 0.2.2, the installed CLI was
0.2.1 and was refused by the floor its own publish had raised. That was an ordering
mistake rather than a defect, but reinstalling is what exposed the pinning gaps.

## Phase 3 — Tests

| Gate | Result |
|---|---|
| `make test` (unit, `-race`) | pass — 9 packages |
| `make e2e` | pass |
| `make lint` (`golangci-lint` v2.12.2) | 0 issues |
| `shellcheck install.sh` | clean |

Verified by hand, because no test covers `install.sh`: `--dry-run` prints the fingerprint
and passes it to `build-static`; a real install produces a CLI *and* a GUI with the
fingerprint compiled in; and the reinstalled 0.2.2 binaries then read the store whose
floor had refused their predecessors.

**This is the gap worth naming.** `install.sh` has no automated coverage at all, so the
claim that an ordinary install now pins the key rests on one manual check on one machine.
The path that matters most — a machine with no key, which must still build and still
refuse store binaries — was reasoned about, not exercised.

## Phase 4 — Code quality

The key-creation branch and the fingerprint-read branch were one block and are now two,
because they answer different questions: whether to make a key, and whether there is one
to trust. Splitting them is what made the ordinary-install case expressible.

---

## Phase 5 — Security review

**Verdict**: PASS

- **Dependency scan**: `govulncheck` (Go 1.25.12) — code affected by 0 vulnerabilities.
  No dependency moved; no Go code changed.
- **Trust change, stated plainly**: this makes an ordinary install on the signing machine
  trust store binaries signed by that key, where before it trusted none. That is the
  intended meaning of keeping the key there, but it is a widening of what the installed
  binary will execute, and it takes effect on any machine holding
  `~/.config/angou/release-signing.asc`. A machine with no key is unaffected.
- **No secret is read or printed**: `gpg --show-keys` reads the public half of the key
  file; only the fingerprint reaches stdout, which is public by design and already
  appears in every signature in the store.
- **Failure mode**: an unreadable key aborts a publishing run and only warns otherwise,
  so a corrupt key cannot silently produce a release signed by nothing.
- **Secrets**: none committed. The signing key itself remains outside the repository and
  is not touched by this change.

---

## Phase 5.5 — Release safety

Rollback is `git revert` plus a rebuild. Nothing in a store changes, so no floor moves
and no other machine is affected until it reinstalls.

Not published: the 0.2.2 artifacts in the store are unaffected by an installer fix, and
the store's floor stays at 0.2.2 until someone runs `angou release` again.

---

## Limitations

- `install.sh` is untested by anything but hand. See Phase 3.
- The pinning was verified by finding the fingerprint in the built binaries, not by
  bootstrapping a bare machine from the store with them. `make e2e-container` was not
  re-run.
- The signing key is still on this machine. Moving it offline remains the control the
  README describes, and this change makes the local install depend on its presence.
