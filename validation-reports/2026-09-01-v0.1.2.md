# Validation report — angou v0.1.2

**Date**: 2026-09-01
**Commit**: the release commit bumping `VERSION` and `README.md` to 0.1.2
**Spec**: [001](../specs/001-angou-format-keying-and-store.md), amended by R6.3.1
**Scope**: the keyring backend. No format, key model, or store layout change.

---

## Summary

angou now reaches the keyring through the cross-desktop Secret Service API, with the
KDE-specific API retained as a fallback. This is a portability fix rather than a
protocol preference: the previous implementation spoke only `org.kde.kwalletd6`, so on
any non-KDE desktop `keyring.Available()` reported nothing and R2.5's fallback applied —
the user typed the recovery passphrase on every command, not because the machine had no
secret store but because angou could not speak to the one it had.

The change was requested after a user carried a store to a second machine and observed
that the keyring integration was tied to one desktop.

## Phase 3 — Tests

| Gate | Result |
|---|---|
| `make test` (unit, `-race`) | pass — 7 packages |
| `make e2e` | pass — 76 tests |
| `make e2e-keyring` | **pass — 86 tests, no skips** |
| `make e2e-container` | not implemented |
| `make shellcheck` | pass |

`make e2e-keyring` was run for this release and both backends were exercised against
live services on the same machine: `ksecretd` serving `org.freedesktop.secrets`, and
`kwalletd6` serving `org.kde.kwalletd6`. A single parameterised test runs the whole
cycle — set the machine up, use it with no passphrase, remove the entry — against each,
so neither is verified only by inference from the other. Both were confirmed to leave no
item behind.

This closes the gap recorded in the 0.1.1 report, where the keyring path had been
verified by hand but not by the suite.

## Phase 4 — Code quality

`make lint` reports 0 issues. The Secret Service backend is a new file under the
existing build constraint split rather than a change to the KWallet one, which is what
R6.6 anticipated.

Eight keyring tests were updated rather than worked around: `init` now sets the machine
up, so a test whose subject is `bootstrap` starts from `init --no-bootstrap`. The
failures were correct behaviour being detected, not flakiness.

## Phase 5 — Security review

**Dependency scan.** `govulncheck`: no vulnerabilities. No new dependencies; the Secret
Service backend uses the D-Bus library already present.

**Session.** The `plain` algorithm is used rather than the DH-encrypted variant. The
transport is a unix socket already restricted to this user, and an adversary able to
observe message bodies on that bus would already see everything else the session does.

**Prompt handling.** Unlocking a locked collection can require the user to answer a
dialog, reported as a prompt object whose completion arrives as a signal. Awaiting it is
deliberately unbounded, because a person takes as long as they take. The *availability*
probe that decides whether a keyring exists remains bounded and cannot prompt — the
distinction that a hang earlier in development established.

**Attributes.** Items are found by attribute search under a schema of angou's own, so
angou never enumerates or reads items belonging to anything else in the keyring.

**Backend selection.** A misspelt `ANGOU_KEYRING` is refused at start-up, before the
command does any work. Reporting it later would leave a half-made store behind, and
answering "no keyring" to a typo would silently and permanently downgrade the user to
the passphrase path — a fallback should never be reached by accident.

## Phase 5.5 — Release safety

**Rollback**: revert the release commit, or set `ANGOU_KEYRING=kwallet` to pin the
previous behaviour without downgrading.

**Migration**: an entry written by 0.1.1 through KWallet is not found by a Secret
Service search, because the two use different item models. On a KDE machine both APIs
front the same wallet, so the practical effect is that a machine bootstrapped under
0.1.1 may need `angou bootstrap --force` once. This is recoverable with the recovery
passphrase, is what R2.4 already describes for a missing entry, and the tool reports the
state rather than prompting unanswerably.

## Known gaps

- Verified against `ksecretd` only. gnome-keyring is the other major implementation and
  is the reason for the change; it has not been tested, and the desktops this release is
  meant to unblock are exactly the ones not yet exercised.
- `make e2e-container` is a target with no implementation.
- The macOS Keychain backend is deferred; R2.5 covers the interim.
- The desktop navigator is not started.
